## 特性

Apache Kafka 是一个分布式、分区、多副本的提交日志系统。它以 Topic 组织消息，每个 Topic 可分为多个 Partition，每个 Partition 在存储层是一个有序、不可变、可追加的日志。分区可以分布在多个 Broker 上，并通过副本机制提供容错。生产者将消息追加到 Partition 末尾，消费者通过 Offset 位置读取消息，Offset 可由消费者提交或根据自动提交配置管理。

Kafka 将消息持久化到磁盘，并通过顺序 I/O、批量读写和零拷贝等技术实现高吞吐和较低延迟。消息默认在集群中保留一段时间或达到一定大小后才被清理，因此与“消费后即删除”的传统队列不同，Kafka 允许新消费者从历史位置重新读取消息，也支持多个消费者组独立消费同一 Topic。

Kafka 的消费模型以 Consumer Group 为核心。一个分区在同一组内只分配给一个消费者，从而在分区级别保证顺序；同组消费者数量增加时，可通过增加分区实现水平扩展。同时，Kafka 提供 Kafka Connect 用于与外部系统进行可扩展的数据导入导出，提供 Kafka Streams 用于构建有状态流处理应用，并支持在一定边界内实现端到端 Exactly-Once 语义。

## 适用场景

Kafka 适合作为高吞吐、可扩展的消息总线和异步通信层。在微服务、事件驱动架构中，Kafka 可以承接服务之间的异步消息，实现削峰填谷、系统解耦和背压缓冲。其多副本和持久化能力使其适合承载关键业务事件流。

Kafka 也适合构建实时数据管道，用于日志聚合、指标采集、审计事件、用户行为埋点和变更数据捕获等场景。它可以将多个数据源的事件集中后分发到数据湖、数据仓库、搜索引擎、监控系统或分析平台，形成统一的数据流入口。

此外，Kafka 可作为流处理和事件溯源的基础。应用可以通过 Kafka Streams 或外部流处理框架读取 Topic 中的事件流进行实时计算、状态管理、窗口聚合和事件回放，适用于实时推荐、风控、订单状态跟踪等场景。

## 部署形态

Apache Kafka 通常部署为多 Broker 分布式集群。Broker 承担分区数据的存储和服务请求，Topic 的分区和副本会分布在多个 Broker、机架或可用区上，以实现容量扩展和故障转移。生产环境通常建议使用多个 Broker 节点，并合理设置副本因子和最小同步副本数。

元数据管理在较新版本中推荐使用 KRaft 模式，该模式简化了部署并减少了对 Apache ZooKeeper 的依赖；在旧版本和部分存量环境中，仍可使用 ZooKeeper 模式。生产部署需要规划分区数、副本因子、ISR、acks、min.insync.replicas 等参数，以平衡可用性、一致性和吞吐。

Kafka 可以部署在物理机、虚拟机、容器和 Kubernetes 环境中，也常见由云厂商提供兼容 Kafka 协议的托管服务。开发和测试场景中，可使用单节点 Broker 配合命令行工具快速启动；生产环境则建议采用多节点、多磁盘、跨可用区部署，并配套监控、告警和容量管理。

## 局限

Kafka 的分布式日志模型也带来运维复杂度。管理员需要关注 Broker、分区、副本、ISR、存储容量、磁盘吞吐和消费者消费延迟等指标。分区数过多会增加元数据管理、故障恢复和重平衡开销，消费组成员变化时的重平衡也可能短暂影响消费。

Kafka 不擅长传输大文件或超大消息。单条消息大小默认受限，虽然可以通过 Broker、Topic、Producer、Consumer 配置调整，但大消息会显著增加内存、磁盘和网络压力，并可能降低整体吞吐。

Kafka 只保证单个分区内有序，不提供跨分区的全局顺序。如需要全局顺序，通常必须减少到单分区或引入额外设计。它也不提供复杂消息路由、优先级队列、定时延迟投递等高级队列功能。

Kafka 的语义保证依赖配置和使用方式。At-least-once、At-most-once 和 Exactly-Once 有不同的前提和边界，消费者提交 Offset 与实际业务处理之间需要谨慎协调，否则可能出现重复消费或丢失。其批量与拉取模型通常面向高吞吐场景，在极低延迟硬实时场景中不一定优于专用低延迟消息系统。
