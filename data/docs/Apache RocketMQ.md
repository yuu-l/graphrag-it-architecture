## 特性

Apache RocketMQ 是一个分布式消息中间件，采用 Topic/Queue 模型，支持发布订阅、集群消费与广播消费。消息持久化存储在 Broker 侧，并支持消息重试与死信处理，默认提供至少一次投递保障。

RocketMQ 提供多种消息类型：普通消息、顺序消息、事务消息、延迟/定时消息，并支持批量发送、请求-应答消息和消息过滤。5.x 版本引入 Proxy 组件，通过 gRPC/Remoting 协议统一接入，增强多语言客户端和云原生场景的接入能力。

高可用方面，RocketMQ 支持主从复制、同步/异步刷盘；5.x 的 Controller 模式提供基于 Raft 的自动故障切换，降低人工干预成本。Broker 支持横向扩展，通过队列分布提升并行处理能力。

## 适用场景

异步解耦：将不依赖实时结果的业务流程异步化，例如通知、审计、积分处理等，降低系统间耦合，提高整体可扩展性。

流量削峰：在促销、秒杀等突发流量场景中将请求写入消息队列，后端服务按自身消费能力处理，保护下游系统不被瞬时流量压垮。

事件驱动与数据分发：作为事件总线用于实时日志、用户行为、监控数据等场景，配合流式计算或数据同步组件实现事件驱动架构。

分布式事务最终一致性：通过事务消息保证本地事务与消息发送的一致性，适用于订单、支付、库存等需要跨服务最终一致性的业务。

## 部署形态

本地开发模式：可在单机运行 NameServer 与 Broker，适合开发调试和小规模验证，不作为生产高可用方案。

经典集群模式：部署多个无状态 NameServer 节点，Broker 采用主从部署，通过复制保证数据高可用；同步/异步刷盘和复制策略可按可靠性需求调整。客户端通过 NameServer 获取路由信息并访问 Broker。

5.x 推荐引入 Controller 和 Proxy：Controller 负责维护主备状态并自动切换，Proxy 承担协议转换和接入层职责。RocketMQ 也支持通过 Docker 镜像、Kubernetes Operator/Helm 等方式容器化部署，具体以官方文档提供的部署方式为准。

## 局限

顺序消息仅保证队列内有序；若需要全局有序，通常只能使用单队列，这会限制吞吐和水平扩展能力，需要在有序性与扩展性之间进行取舍。

默认投递语义为至少一次，端到端精确一次需要消费端幂等、事务消息或业务去重机制配合；事务消息主要解决生产者本地事务与消息发送的原子性，不覆盖消费者侧处理结果。

消息持久化依赖本地磁盘，堆积能力受存储容量和清理策略限制，不适合长期大规模历史消息回放或当作数据库、数据湖使用。单条消息大小有默认上限，大文件应使用对象存储并传递引用。

多组件部署带来一定运维复杂度，需要关注监控、容量规划、参数调优和升级管理。跨集群、跨地域复制等高级能力通常需要额外部署和配置。
