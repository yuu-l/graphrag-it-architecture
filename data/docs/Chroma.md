## 特性

Chroma 是一个开源的 AI 原生向量数据库，官方也称其为 embedding database。其核心抽象是 collection，每个 collection 可保存 documents、embeddings、metadatas 和 ids，并提供向量相似度检索、元数据过滤以及距离或相关性分数返回。官方文档强调其设计目标是为 AI 应用提供简单、可嵌入的存储与检索能力。

Chroma 提供 Python 和 JavaScript/TypeScript 客户端，API 相对简单。用户可以直接写入原始文本，由 Chroma 的内置默认嵌入函数在本地生成向量，降低快速原型阶段的门槛；也可以传入自定义 embedding function，对接 OpenAI、Cohere、Hugging Face 等外部模型或自托管模型。

Chroma 支持本地持久化，数据可以写入本地路径，同时也能以客户端-服务器模式运行并由客户端远程连接。检索结果可包含文档内容、元数据和距离，配合 where 过滤条件缩小候选集。它与 LangChain、LlamaIndex 等 AI 框架有广泛集成，常被用作 RAG 系统的向量检索层。

该组件功能边界集中在向量检索与元数据过滤，而不是通用 SQL 或事务数据库。官方将其定位为 AI 原生数据库，强调开箱即用和快速原型能力。

## 适用场景

Chroma 适合语义搜索和检索增强生成（RAG）场景：将私有知识库、手册、网页或文档分块后写入 collection，查询时检索与问题最相关的片段，再将片段交给大模型生成答案。其内置嵌入和简单 API 适合快速搭建这类应用。

适合中小规模团队和个人开发者进行快速原型、MVP 或单机生产应用。若应用的数据规模和查询吞吐有限，并且团队希望减少基础设施复杂度，Chroma 可以在进程内或单节点服务中直接运行。

适合本地优先或数据敏感场景：嵌入式模式下数据可保存在本地目录，适合桌面应用、Jupyter Notebook、测试环境、CI 流水线以及不希望将数据上传到外部向量库的情况。

也适用于相似项推荐、去重以及需要对向量进行快速最近邻查找的场景。若应用需要复杂关系查询、事务处理、大规模分布式扩展或企业级权限体系，则不适合以 Chroma 作为主要存储。

## 部署形态

嵌入式模式：在应用进程内使用 Chroma 客户端，例如 Python 的持久化客户端，将数据存储在本地路径。没有独立服务进程，适合开发、单机工具和测试。也可以使用临时或内存模式进行快速实验。

客户端-服务器模式：通过 `chroma run` 或 Docker 启动 Chroma 服务端，客户端使用 HTTP 连接。服务端可以部署在本地或远程主机，便于多个应用共享同一个向量库，也可以把数据目录挂载到持久化存储。

Chroma Cloud：官方提供托管云服务，用户创建租户、数据库和 API Key 后通过客户端连接，免去服务端运维。该模式适合希望使用 Chroma API 但不维护基础设施的团队。

自托管：官方提供 Docker 镜像和部署说明，通常以单节点方式运行，并挂载持久化卷保存数据。需要自行处理备份、升级、安全暴露和访问控制等运维事项。

## 局限

Chroma 不是面向超大规模、分布式集群场景设计的向量数据库。自托管部署通常以单节点为主，横向扩展能力和高可用能力有限；若数据量、写入吞吐或查询 QPS 很大，需要评估其容量和延迟是否满足要求。

查询能力主要围绕向量相似度检索和元数据过滤，where 过滤器更适合结构化元数据条件，不适合承担复杂 SQL、聚合、连接或事务分析任务。它不是通用关系数据库的替代品。

在嵌入式和单节点部署下，并发写入和多进程共享同一数据目录需要谨慎，可能出现锁定或一致性限制。元数据过滤的复杂程度也有边界，一些嵌套结构或高级过滤语义可能不被完整支持。

Chroma 的功能和生态演进较快，API 与集成可能随版本变化；本地自托管的安全认证、多租户和权限模型相对有限，企业级 RBAC、审计和细粒度隔离需结合实际部署或官方托管云评估。
