## 特性

Prometheus 的核心数据模型是多维时间序列模型。每条时间序列由指标名称和一组键值对标签唯一标识，标签可以表达实例、服务、环境等维度，使同一指标能够被灵活地过滤、聚合和关联。

Prometheus 提供 PromQL 查询语言，用于对采集到的时间序列进行切片、聚合和查询。其架构不依赖分布式存储，单个 Prometheus server 节点自治运行，能够独立完成数据抓取、存储和查询，不依赖网络存储或其他远程服务。

数据采集默认采用基于 HTTP 的拉取模型。Prometheus 通过静态配置或服务发现获得目标列表，从目标暴露的 HTTP 端点抓取指标。对于短生命周期任务等无法直接抓取的场景，可通过 Pushgateway 中间网关推送时间序列。可视化方面支持内置表达式浏览器、Grafana 集成和控制台模板等多种形式。

## 适用场景

Prometheus 适合记录任何纯数值的时间序列数据。无论是机器中心的主机指标，还是应用自定义的数值型业务指标，只要能够表达为随时间变化的数值，都可以由 Prometheus 采集、存储和查询。

Prometheus 特别适合高度动态的面向服务架构和微服务环境。其多维数据模型和服务发现能力能够跟随实例变化，支持按服务、实例、环境等标签进行组合查询与聚合，适合容器化、多实例和持续发布场景。

Prometheus 的设计强调可靠性，目标是成为故障期间仍然可用、可以快速诊断问题的系统。由于单个 Prometheus server 不依赖网络存储或其他远程服务，在部分基础设施异常时，仍可就地查询已经采集到的指标。

## 部署形态

Prometheus server 通常以独立进程或容器方式部署，核心是单个自治 server。它通过静态配置或服务发现获取目标，使用 HTTP 拉取指标，并将时间序列保存在本地；查询和告警规则评估都基于该本地数据完成。

被监控目标需要以 Prometheus 文本格式暴露指标 HTTP 端点。对于批处理、短生命周期任务等无法被可靠抓取的目标，可以先将指标推送到 Pushgateway，再由 Prometheus server 抓取。目标发现支持 Kubernetes、Consul、EC2 等机制，也可使用静态文件配置。

可视化与告警方面，Prometheus 官方支持内置表达式浏览器、Grafana 集成和控制台模板。告警规则由 Prometheus server 评估并触发，可交给 Alertmanager 进行去重、分组和通知路由，形成完整的监控告警链路。

## 局限

Prometheus 不适合要求 100% 数据准确性的场景。官方文档明确以按请求计费为例：Prometheus 采集到的数据可能不够详细和完整，不应作为计费或审计的权威数据源，而应由专用系统进行计费数据采集和分析，Prometheus 则用于监控目的。

Prometheus 面向纯数值时间序列，并非通用日志、事件或追踪系统。对于任意文本日志、逐事件数据或请求级追踪数据，应使用专门的日志、追踪或事件系统，再将可由数值指标表达的结果交给 Prometheus 监控。

此外，官方设计强调单个 server 节点的自治和不依赖分布式存储，因此 Prometheus 本身不提供内置的分布式存储或集群复制能力。这一设计偏向故障期间的可靠性和可用性，而不是为跨节点全局存储提供原生集群能力。
