## 特性

RabbitMQ 是一款开源消息代理，同时提供流式消息能力。它原生支持 AMQP 0-9-1，并通过插件支持 AMQP 1.0、MQTT 3.1/3.1.1/5.0 和 STOMP 等协议，使不同技术栈的应用、设备和网关能够统一接入。RabbitMQ 提供灵活的路由模型：生产者将消息发布到 Exchange，Exchange 根据 direct、fanout、topic、headers 等类型及绑定规则将消息路由到一个或多个队列，并支持 Exchange 间绑定。

在可靠性方面，RabbitMQ 提供持久化消息与持久队列、发布确认、消费者确认等机制，并通过镜像队列和仲裁队列实现队列数据冗余。仲裁队列基于 Raft 共识协议，提供更强的数据一致性与故障恢复能力。RabbitMQ 还提供 Stream，用于可重放、日志型消息场景。

在运维与观测方面，RabbitMQ 提供管理界面、管理 HTTP API、命令行工具、虚拟主机、用户权限、策略、资源限制、Prometheus 指标、Grafana 模板和分布式追踪等能力。其插件体系允许按需启用协议、认证、管理、联邦和 Shovel 等功能。

## 适用场景

RabbitMQ 适用于应用解耦与异步集成。系统间通过消息传递事件或命令，可以降低同步调用带来的耦合度，提升可用性和扩展性。典型场景包括微服务间通信、订单处理、通知发送、批处理任务投递等。

RabbitMQ 适合需要可靠投递和复杂路由的业务场景。例如需要按主题、路由键或头信息将消息分发到不同消费者，或需要死信队列、TTL、优先级队列，以及通过插件实现延迟队列。其多协议支持也适合 IoT 和移动端接入，例如通过 MQTT 接收设备数据，再由后端 AMQP 应用消费。

RabbitMQ 还可用于请求/响应通信和事件驱动架构。对于需要可重放、日志型消息的场景，可以评估 RabbitMQ Stream。但对于海量日志聚合、长期历史回放和高吞吐分区流处理场景，建议与专门日志或流平台进行对比，不宜简单视为替代方案。

## 部署形态

RabbitMQ 支持单节点部署。单节点适用于开发、测试或低风险环境，官方提供 Debian/RPM 包、通用 Unix 二进制包、Windows 安装器和 Docker 镜像。生产环境通常建议使用 Linux，并配置持久化存储、监控和资源限制。

多节点集群是生产环境的常见形态。集群节点共享用户、虚拟主机、权限等元数据，队列可以通过策略进行镜像复制，或使用仲裁队列跨节点复制数据，以提升可用性。集群部署需要规划节点命名、主机名解析、Erlang cookie、网络端口和负载均衡。

在 Kubernetes 上，官方提供 RabbitMQ Cluster Operator，用于声明式部署和管理 RabbitMQ 集群，支持扩缩容、滚动升级和持久化。也可以使用 Docker 或虚拟机、物理机方式部署。无论采用何种形态，都应结合管理界面、Prometheus 和日志系统进行监控与告警。

## 局限

RabbitMQ 的单个队列吞吐能力受限于承载该队列的节点及其复制机制。镜像队列存在复制开销，仲裁队列由于 Raft 多数确认会带来更高的写入延迟。因此，在对单队列或单分区有极高吞吐、低延迟和大规模并发写入要求的场景下，需要谨慎评估，或采用分片、多队列等设计。

传统队列在消息被确认后即删除，不提供原生消息回溯和历史重放能力。RabbitMQ 的 Stream 虽然提供可重放日志语义，但其吞吐模型和生态与 Kafka 等日志型系统仍有差异。需要长期保存并顺序消费大量历史数据的场景应评估是否适合。

消息顺序保证只在特定条件下成立，例如单一生产通道、单一队列、单一消费者时较容易保持。多消费者、重试、死信和优先级等机制可能改变实际消费顺序。业务方通常需要采用幂等、序列号或拆分队列等方式保证最终一致。网络分区是集群部署必须处理的运维问题，需要配置分区处理策略，否则可能导致脑裂、发布阻塞或镜像不同步。

资源保护方面，RabbitMQ 会通过内存和磁盘水位线阻断发布者，以避免节点崩溃。这意味着消息大量堆积或消费者处理不及时时会直接反压上游。需要做好容量规划、队列长度限制和流量控制，以避免系统级联不可用。
