## 1. 背景与动机

本项目的技术蓝本来自一个真实业务场景（`other.md` 描述的配送配置平台），其核心痛点具备通用性，可完整迁移到
**中小企业 IT 架构选型**这一更通用、更贴合个人简历的业务方向上。

**背景（STAR 法则 - Situation）**

中小企业在建设 IT 系统时，需要做技术选型与架构方案设计：选哪些组件（Web 服务器、应用框架、数据库、缓存、
消息队列、搜索、存储、负载均衡、监控）、怎么组合、采用什么部署形态（单机 / 主从 / 集群）。这个过程看似简单，
实际上配置项多、维度多、规则复杂，通常依赖架构师或资深研发的经验，中小企业往往不具备这样的人才。

**挑战（Task）**

1. **配置项多、维度多**：组件（数据库、缓存、MQ 等十余类）叠加维度（预算、规模/并发、可用性、一致性、部署形态），
   组合后可达数百个配置决策点。
2. **依赖/互斥/组合关系复杂**：组件间存在依赖（应用框架依赖数据库）、互斥（MySQL ↔ PostgreSQL 二选一）、
   影响（缓存增强读性能、MQ 降低耦合削峰）等关系，牵一发而动全身。
3. **人工决策效率低、易错**：选型者需要频繁查阅组件文档、对比优劣、咨询研发，既慢又容易选错，选错代价极大
   （性能撑不住 → 宕机；过度设计 → 浪费成本；一致性选错 → 数据事故）。

**行动（Action）**

设计并实现一个 **GraphRAG + 大模型推理** 的智能配置助手：将散落在文档中的组件选型知识结构化为知识图谱，
实现"组件—依赖—互斥—影响—适配"等要素之间的关联查询；用大模型的自然语言理解与逻辑推理能力，对用户诉求
（业务场景 + 预算 + 规模 + 可用性）生成合规的架构方案，并对生成结果做规则兜底校验。

**结果（Result，目标）**

- 架构选型/方案生成从「人工查文档 + 咨询研发」的 10+ 分钟量级，压缩到分钟级。
- 通过规则校验消除明显不合规的方案（依赖缺失、互斥冲突、维度不合法），显著降低误配率。

## 2. 问题定义

把一个依赖人力的、容易出错的「IT 架构选型」过程，升级为「**结构化知识 + 可控推理**」的智能配置系统。

核心要解决的三个问题：

1. **知识召回**：用户口语化、多样化的表达，如何稳定命中分散在文档中的组件选型知识。
2. **关系推理**：如何在召回时利用组件之间的依赖/互斥/影响关系做结构化扩展（而非纯向量相似度）。
3. **方案可信**：大模型生成的架构方案，如何保证不违反业务约束（依赖、互斥、维度合法性）。

---

## 3. 目标用户

| 用户 | 场景 | 诉求 |
|------|------|------|
| 中小企业 IT 负责人 / 运维 | 公司要上线新系统，不知道该选什么技术栈 | 快速获得合规的架构方案 |
| 初级/中级研发 | 被要求做技术选型，经验不足 | 理解组件效果、依赖与互斥 |
| 架构师助理 | 已有方案基础上做预算/规模调整 | 方案优化与调整建议 |

> 注：作为个人项目，本系统的直接用户是「演示者 + 面试官」，核心价值是清晰展示 GraphRAG 的工程解法。

## 4. 功能需求（FR）

### FR-1 配置/规则效果解释（explain 意图）

- 用户提问某组件/规则的作用、影响、依赖、互斥关系。
- 例：「Redis 缓存对数据库有什么影响？」「MySQL 和 PostgreSQL 有什么区别，怎么选？」
- 输出：结合图谱关系三元组 + 召回文本段的解释性回答。

### FR-2 基于业务目标生成架构方案（generate 意图）

- 用户描述业务场景与约束（场景、预算档位、规模/并发、可用性等级）。
- 例：「我要做一个日活 5000 的电商网站，预算每月 5000，要 99.9% 可用，帮我出一套架构方案。」
- 输出：组件清单 + 部署形态 + 选型理由（结构化 `ConfigProposal`），并经过规则校验。

### FR-3 在已有方案基础上的优化调整（optimize 意图）

- 用户基于既有方案提出调整诉求（预算砍半、规模翻倍、去掉某组件）。
- 例：「在上面方案基础上，预算砍半怎么调？」「不要消息队列的话，还能保证削峰吗？」
- 输出：调整后的方案 + 调整理由 + 影响说明。

### FR-4 无效问题过滤（unknown 意图 / fallback）

- 当用户问题超出「IT 架构选型」领域时，直接引导用户重新提问，不进入完整检索与推理链路，
  减少无效处理与 token 消耗。

### FR-5 多轮上下文（上下文缓存）

- 同一会话内，后续提问若与历史相关，则复用历史上下文（命中实体、配置项、问答），
  支持连续对话与增量推理；并在检索阶段对已命中实体做去重剪枝，降低重复检索与噪声。

## 5. 非功能需求（NFR）

### NFR-1 可运行端到端（必达）

- `docker compose` 起服务 → 离线建图建索引 → 在线问答，跑通一条完整链路，可现场演示。
- 不要求生产级性能，但要求流程完整、逻辑正确、可复现。

### NFR-2 可配置、不写死（必达）

- LLM 的 `base_url`、`api_key`、`model` 全部从 `.env` 读取，代码任何地方不得写死。
- embedding 模型名、检索参数（top-k、阈值、跳数）同样可配置。
- 走 OpenAI 兼容接口，默认 DeepSeek，可切换为 Qwen / OpenAI / Kimi 等。

### NFR-3 可量化指标（必达）

- 至少产出一组可量化指标：意图识别准确率、检索 recall@k（有/无图谱对比）、生成方案规则合规率。

### NFR-4 代码质量（约束）

- 所有 IO 异步；日志用 loguru；层间通信用 Pydantic 模型；不绕过层边界。
- 每个功能/阶段通过测试（≥80% 覆盖率目标）才进入下一阶段。

## 6. 范围边界（In / Out of Scope）

**In Scope**

- GraphRAG 离线构建（切块、向量、BM25、知识图谱、实体向量）。
- 在线两阶段检索（实体链接 + 图谱扩展 + 混合召回 + 融合）。
- 意图识别、差异化生成、规则兜底校验。
- Redis 上下文缓存、FastAPI 后端、CLI demo、评估脚本。

**Out of Scope（本版本不做）**

- 前端工程（仅提供 REST API + CLI demo；见 `FRONTEND_GUIDELINES.md`）。
- 生产级高可用、权限/鉴权、多租户、限流（个人项目不涉及）。
- 大规模真实语料（使用人工策划的种子文档/图谱，约 15~25 组件 + 15~20 篇文档）。

## 7. 指标体系（对齐 other.md 的两层测评）

**第一层：过程指标（系统能力）**

| 模块 | 指标 | 目标 |
|------|------|------|
| 意图识别 | 准确率 | ≈ 98% |
| RAG 检索 | recall@k（引入图谱后） | ≈ 95%（无图谱基线 ≈ 70%，用于对比叙事） |
| 大模型生成 | 答案准确率 / 指令遵循率 | ≈ 95% / ≈ 98% |

**第二层：结果指标（业务落地效果）**

- 方案生成耗时对比（人工 vs 系统）。
- 方案错误（依赖/互斥/维度违规）修复率。
- 新人上手时间（熟悉选型规则所需时间）。

> 说明：结果指标作为"叙事用"口径写入文档与 README；过程指标须用评估脚本在 `data/eval/` 上真实跑出。
