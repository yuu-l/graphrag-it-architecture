# 应用流程文档（APP_FLOW）— GraphRAG 中小企业 IT 架构智能配置助手

> 本文描述系统的端到端流程：离线准备（构建期）与在线执行（问答期），以及三类意图的完整用例链路。

---

## 1. 总体流程概览

```
                    ┌─────────────────────────────────────────────┐
                    │                离线准备（构建期）              │
                    │  docs → chunk → vector(FAISS) → BM25(ES)     │
                    │                     ↘ 实体/关系 → Neo4j      │
                    │                     ↘ 实体向量 → FAISS       │
                    └─────────────────────────────────────────────┘
                                          │ 一次性构建，产出索引与图谱
                                          ▼
   用户 query ──► ┌─────────────────────────────────────────────┐
                  │                在线执行（问答期）              │
                  │  意图识别 → 实体链接 → 图谱1~2跳扩展           │
                  │  → 混合召回(向量+BM25) → 融合排序 → 生成 → 校验 │
                  │  （上下文缓存 Redis 贯穿多轮）                 │
                  └─────────────────────────────────────────────┘
                                          │
                                          ▼
                                 结构化回答 / 架构方案
```

系统是**两段式**：离线阶段把非结构化的选型知识固化为「图谱 + 双索引」，在线阶段基于这些产物做
「结构化、可解释」的检索增强生成。

---

## 2. 离线准备流程（构建期）

由 `scripts/build_offline.py` 一键编排，共 6 步：

1. **原始文档采集与规范化**
   - 输入：`data/docs/` 下的组件选型说明、规则说明、架构方案文档（Markdown，人工策划 15~20 篇）。
   - 处理：统一转为结构化纯文本。

2. **语义驱动的文档切块**
   - 以「一个组件描述 / 一条选型规则」为最小切分单元，而非固定窗口。
   - 单 chunk 100~300 字，确保能独立表达一个配置项的作用、适用范围、关键约束。
   - 产物：chunk 集合，作为向量/关键词/图谱三者共同的来源。

3. **向量索引构建（语义召回层）**
   - 用 bge embedding（本地 sentence-transformers，模型名可配置）为每个 chunk 生成向量。
   - 存入 FAISS（chunk 表）。

4. **关键词索引构建（精确兜底层）**
   - 基于原始 chunk 文本构建 BM25 索引，存入 Elasticsearch。
   - 用于精确命中组件名称、规则描述、参数阈值等显式知识。

5. **知识图谱构建（结构化推理层）**
   - 实体抽取：LLM 结合预定义 schema（见 `BACKEND_STRUCTURE.md` §4）抽取组件/类别/场景/需求/部署形态等实体。
   - 关系抽取：依赖（DEPENDS_ON）、互斥（MUTUAL_EXCLUSIVE）、影响（ENHANCES）、适配（SUITABLE_FOR）、归属（INSTANCE_OF）。
   - 实体消歧与合并：别名合并，形成稳定实体 ID（首版以人工种子 `data/seed/*.yaml` 为主，LLM 抽取为辅）。
   - 图谱存储：Cypher 写入 Neo4j，支持 1~2 跳关系扩展。

6. **实体向量索引构建（实体链接层）**
   - 为图谱实体单独建向量索引：embedding 文本 = 标准名 + 别名 + 简要描述 + 业务标签。
   - 存入 FAISS（entity 表），作为在线第一阶段的输入。

## 3. 在线执行流程（问答期）

### 3.1 意图识别（前置路由）

- 在进入完整检索前，用轻量 LLM 调用对用户问题分类（三类意图 + 无效问题）。
- 三类意图：`explain`（效果解释）、`generate`（生成方案）、`optimize`（方案优化）。
- `unknown`：超出领域 → 直接引导重新提问，跳过后续检索/推理，省 token。

### 3.2 第一阶段：实体识别与图谱扩展

1. 对 query 做语义对齐：在实体 FAISS 索引中召回语义最相近的实体候选，取 top-k（默认 5，可配置）。
2. 用召回实体在 Neo4j 中按预定义关系类型（依赖/互斥/影响/适配）做 1~2 跳扩展，得到实体子图。

> 目标：把自然语言稳定映射到结构化、可解释的实体子图空间。

### 3.3 第二阶段：基于实体子图的混合检索

1. 以子图中各实体的描述为查询向量，做候选文本召回：
   - 向量相似度召回（FAISS）→ top-k 候选文本段。
   - BM25 关键词召回（ES）→ 精确命中组件名/规则描述。
2. 加权融合排序：对两路结果合并去重，用 RRF（Reciprocal Rank Fusion）加权打分排序。
3. 生成参考上下文：对融合结果设相似度阈值，过滤低相关文本段，取高置信度知识；
   结合图谱中的实体关系三元组（文本形式），作为 LLM 生成的参考上下文。

> 目标：在保证召回覆盖率的同时，降低无关文本对推理的干扰。

### 3.4 生成

- 将「用户问题 + 参考上下文（召回文本 + 关系三元组）+ 历史对话摘要」统一传给 LLM。
- 按意图选择差异化 prompt 模板（各模板内置思维路径约束 + 少样本示例）。

### 3.5 规则兜底校验（仅 `generate`/`optimize` 涉及具体方案时）

- 对 LLM 生成的架构方案做确定性检查（不依赖 LLM）：
  - 依赖关系：每个组件的依赖是否被满足。
  - 互斥关系：是否同时选了互斥组件（如 MySQL 与 PostgreSQL）。
  - 维度合法性：预算/规模/可用性/部署形态与组件是否匹配。
- 发现冲突则修正或明确提示，保证输出方案业务正确、可落地。

### 3.6 上下文缓存（贯穿多轮）

- 每轮记录：用户问题、系统回答、命中实体集合、当前涉及的配置项，结构化存入 Redis（按会话维度）。
- 后续提问若与历史相关，从 Redis 选取相关轮次上下文，拼成精简上下文传给 LLM。
- 参与检索去重剪枝：当前轮召回实体已在历史集合中，则跳过对该实体的重复召回与扩展。

## 4. 三类意图的完整用例链路

### 用例 A：效果解释（explain）

```
用户：「Redis 缓存对数据库有什么影响？」
意图 → explain
实体链接 → [Redis, 数据库]
图谱扩展 → Redis -[ENHANCES]-> 读性能；Redis -[DEPENDS_ON]-> 数据库数据
混合召回 → 命中「缓存」「读写性能」相关 chunk
生成 → 解释性回答（结合关系三元组）
```

### 用例 B：生成方案（generate）

```
用户：「日活 5000 的电商，预算每月 5000，要 99.9% 可用，出一套架构方案」
意图 → generate
实体链接 → [电商(场景), 高可用(需求), 中规模(规模)]
图谱扩展 → 电商 -[SUITABLE_FOR]-> {Nginx, FastAPI, MySQL, Redis...}；
           高可用 -[SUITABLE_FOR]-> 主从/集群形态
混合召回 → 召回相关组件的选型说明 chunk
生成 → ConfigProposal（组件清单 + 部署形态 + 理由）
规则校验 → 检查依赖/互斥/维度合法性 → 通过
输出 → 结构化方案
```

### 用例 C：方案优化（optimize）

```
用户（多轮）：「在上面方案基础上，预算砍半怎么调？」
意图 → optimize
上下文缓存 → 命中上一轮的方案（组件 + 形态 + 约束）
实体链接 → [预算(需求)]，且去重剪枝（跳过上一轮已命中实体）
混合召回 → 召回低成本替代组件 chunk
生成 → 调整后的方案 + 影响说明
规则校验 → 校验调整后仍满足依赖/互斥/维度 → 通过
```

### 用例 D：无效问题（unknown）

```
用户：「今天天气怎么样？」
意图 → unknown → 直接引导：「请描述您的业务场景、预算与规模，我来帮您做 IT 架构选型」
（不进入检索与推理，省 token）
```

## 5. 在线链路状态流转（LangGraph StateGraph）

```
entry
  │
  ▼
[intent]（意图识别）
  ├─ unknown ──────────────────────────────► [fallback]（引导重问）──► END
  └─ explain / generate / optimize
        │
        ▼
[entity_link]（实体向量召回 top-k）
        │
        ▼
[graph_expand]（Neo4j 1~2 跳扩展 → 实体子图）
        │
        ▼
[hybrid_retrieve]（FAISS 向量 + ES BM25 → RRF 融合 → 阈值过滤）
        │
        ▼
[generate]（按意图选模板，LLM 生成）
        │
        ├─ explain ─────────────────────────► END
        └─ generate / optimize
                │
                ▼
[validate]（规则兜底校验 → 修正/提示）
                │
                ▼
               END
```

`DialogState`（图状态，Pydantic 模型）承载：`query`、`session_id`、`intent`、`linked_entities`、
`entity_subgraph`、`retrieved_context`、`answer`、`proposal`、`validation_report` 等字段。
